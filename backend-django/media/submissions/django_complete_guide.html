3.1 — MVC Architecture & Django's MTV

The blueprint every web framework follows

🍕 Real-World Analogy

Think of a restaurant. The Menu (Model) lists all available dishes and their recipes. The Waiter (Controller/View) takes your order, talks to the kitchen, and brings your food. The Plate Presentation (View/Template) is how your food looks when it arrives. Each role is separate — the menu doesn't care how food is plated, the waiter doesn't cook.

What is MVC?

MVC separates an application into 3 parts so that changes in one part don't break the others. It's the foundation of almost every web framework.

The MVC Request-Response Cycle

Django's MTV — Same Idea, Different Names

Django uses MTV but it means the same thing as MVC. Django just renamed "Controller" to "View" and "View" to "Template" — confusing at first, but the concept is identical.

MVC NameDjango MTV NameWhat It DoesExample File
ModelModelDefines database structure, handles datamodels.py
ViewTemplateRenders HTML — what the user seeschallenge.html
ControllerViewBusiness logic — receives request, calls model, picks templateviews.py
⚠️ Common Exam Trick: Django's "View" = MVC's "Controller". Django's "Template" = MVC's "View". Don't mix them up!

Benefits of MVC / MTV

🔀 Separation of Concerns

Each part does one job only. Clean, organized code.

🧪 Testability

Test each component independently without the others.

👥 Parallel Work

Frontend and backend developers work simultaneously.

♻️ Reusability

Models and templates can be reused across the app.

🔧 Maintainability

Changes in one part don't break the others.

📈 Scalability

Individual components can scale independently.

The Full Request-Response Steps

1

User Action

User clicks a link or submits a form in their browser.

2

HTTP Request Sent

Browser sends a GET or POST request to the server URL.

3

URL Routing

Django's urls.py matches the URL to the right View function.

4

View Processes

View receives the request, validates input, calls the Model.

5

Model Queries DB

Model fetches or saves data from the database.

6

Template Renders

View sends data to Template which generates HTML.

7

Response Returned

HTML is sent back to the browser, user sees the page.

3.2 — Role of the Backend

What happens on the server that users never see

🏦 Analogy

A bank's front desk (frontend) looks nice and takes your requests. But the vaults, computers, and security systems (backend) are what actually do the work — checking your balance, processing transactions, verifying identity. Users only see the front desk, but the backend is where everything happens.

🖥️ Frontend (Client Side)

  • Runs in the user's browser
  • HTML, CSS, JavaScript
  • Visible to the user
  • Buttons, forms, layouts
  • Can be inspected/viewed

🔧 Backend (Server Side)

  • Runs on the web server
  • Python, Java, PHP, etc.
  • Hidden from the user
  • Databases, APIs, logic
  • Cannot be seen directly

Core Backend Responsibilities

🚦 Routing

Maps URLs to handler code. When /products/123 is requested, routing decides which Python function handles it.

URL Examples
/home           → homepage view
/products       → product list
/products/123   → product #123
/api/users      → returns JSON
🧠 Business Logic

The rules of your application: calculating discounts, checking permissions, validating data, processing transactions.

Examples: "Only admins can delete", "Discount applies if cart > Rs 1000", "Password must be 8+ chars"

🔐 Security Layers
  • Authentication — Who are you? (Login)
  • Authorization — What can you do? (Permissions)
  • Input Validation — Prevent SQL injection, XSS
  • CSRF Protection — Prevent fake form submissions
  • Rate Limiting — Prevent brute-force attacks
🗄️ Database Management

Reading and writing data permanently. The backend talks to the database, the frontend never does directly (that would be a huge security risk).

3.4 — URLs and Views

Routing requests to the right Python function

📬 Analogy

URLs are like a building's room numbers. When a visitor says "I want Room 302", the building's directory (urls.py) looks up Room 302 and directs them there. The View is what happens inside that room — who talks to the visitor and what they give them back.

How URL Routing Works

User visits /challenges/january/
↓ Django reads urls.py top-to-bottom
First pattern: path('admin/') → No match
Second: path('challenges/') → Match! Include challenges/urls.py
↓ Now check challenges/urls.py
path('<str:month>/') → Match! Call monthly_challenge(request, "january")
↓ View returns HttpResponse

Project URLs (Root)

challenges_project/urls.py
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    # Include app-level URLs — all /challenges/... routes go here
    path('challenges/', include('challenges.urls')),
]

Writing View Functions

challenges/views.py
from django.http import HttpResponse, HttpResponseNotFound
from django.shortcuts import redirect
from django.urls import reverse

monthly_challenges = {
    'january': 'Exercise daily for 30 minutes',
    'february': 'Read one book',
    # ... etc
    'december': None,  # No challenge defined
}

def monthly_challenge(request, month):
    try:
        challenge = monthly_challenges[month.lower()]
        return HttpResponse(challenge)
    except KeyError:
        return HttpResponseNotFound("Month not supported!")

def challenge_by_number(request, month):
    # redirect from /challenges/1/ to /challenges/january/
    months = list(monthly_challenges.keys())
    if month > len(months):
        return HttpResponseNotFound("Invalid")
    redirect_url = reverse('monthly-challenge', args=[months[month-1]])
    return redirect(redirect_url)  # Use reverse() — not hardcoded strings!
💡 Always use reverse() instead of hardcoding URLs like '/challenges/january/'. If you later change the URL pattern, reverse() still works. Hardcoded strings break.

3.5 — Templates & Static Files

Django Template Language (DTL), inheritance, static files

📝 Analogy

A template is like a document form with blank fields. "Dear __name__, your order __id__ has shipped." The Django view fills in the blanks with real data and sends the completed document to the user.

Django Template Language (DTL)

{{ variable }}

Outputs a variable's value. {{ user.name }} → prints the name.

{% tag %}

Control flow. {% for %}, {% if %}, {% url %}, etc.

{{ var|filter }}

Transform values. {{ name|upper }} → JOHN. {{ text|truncatewords:20 }}

Passing Data from View to Template

views.py
from django.shortcuts import render

def monthly_challenge(request, month):
    challenge_text = monthly_challenges[month]
    return render(request, 'challenges/challenge.html', {
        'text': challenge_text,         # Template gets {{ text }}
        'month_name': month.capitalize() # Template gets {{ month_name }}
    })
challenges/challenge.html
<!-- Variable output -->
<h1>{{ month_name|title }} Challenge</h1>

<!-- Conditional tag -->
{% if text is not None %}
    <p>{{ text }}</p>
{% else %}
    <p>No challenge this month!</p>
{% endif %}

Field Options

models.py — Field Options
class Book(models.Model):
    title = models.CharField(max_length=50)
    author = models.CharField(max_length=100, null=True)   # DB allows NULL
    bio   = models.TextField(blank=True)               # Form allows empty
    slug  = models.SlugField(unique=True)               # Must be unique
    rating = models.IntegerField(default=0)              # Default value

⚠️ null vs blank: null=True allows NULL in the database column. blank=True allows empty values in Django forms. They're different! For text fields, prefer blank=True, default="" over null=True.

Filtering & Field Lookups

QuerySet Lookups — Double Underscore Syntax
# You CANNOT do: Book.objects.filter(rating < 3)  ← SyntaxError!
# Use Django's __ (double underscore) lookups instead:

Book.objects.filter(rating__lt=3)           # rating < 3
Book.objects.filter(rating__gte=4)          # rating >= 4
Book.objects.filter(title__contains="Harry") # title contains "Harry"
Book.objects.filter(title__icontains="harry")# case-insensitive
Book.objects.filter(author__startswith="J")  # starts with J
Book.objects.filter(rating__in=[4,5])         # rating is 4 or 5
Book.objects.filter(author__isnull=True)      # author is NULL

# Chaining (AND logic by default):
Book.objects.filter(is_bestselling=True, rating__gt=3)

# OR logic — use Q objects:
from django.db.models import Q
Book.objects.filter(Q(rating__lt=3) | Q(is_bestselling=True))

# Order and aggregate:
Book.objects.order_by('-rating')             # Descending
Book.objects.aggregate(Avg('rating'))         # Average
LookupMeaningSQL Equivalent
__exactExact match= 'value'
__lt / __gtLess/greater than< value / > value
__lte / __gteLess/greater or equal<= value / >= value
__containsSubstring matchLIKE '%value%'
__icontainsCase-insensitive containsILIKE '%value%'
__startswithStarts withLIKE 'value%'
__inIn a listIN (1,2,3)
__isnullIs NULLIS NULL

3.8 — Forms, CSRF, Validation

Handling user input safely

GET vs POST

📤 GET — Reading Data

  • Data visible in URL: ?q=python
  • Bookmarkable, shareable
  • For search, filters
  • Never for passwords!
  • Has length limit

📥 POST — Sending Data

  • Data in request body (hidden)
  • Not bookmarkable
  • For login, registration, file uploads
  • Required for sensitive data
  • No length limit

CSRF — What It Is and Why It Matters

🎭 CSRF Attack Analogy

You log in to your bank. Without logging out, you visit a hacker's site. That site has a hidden form that silently submits "transfer Rs 50,000 to hacker" to your bank. Because your browser still has the bank cookie, the bank thinks it's YOU! This is CSRF. Django prevents it by requiring a secret token in every form.

Every POST Form Needs {% csrf_token %}
<form method="POST" action="{% url 'contact' %}">
    {% csrf_token %}  <!-- This renders: <input type="hidden" name="csrfmiddlewaretoken" value="abc123..."> -->
    <input type="text" name="username">
    <button type="submit">Submit</button>
</form>

Django Forms API

forms.py — Defining the Form
from django import forms

class ContactForm(forms.Form):
    name  = forms.CharField(max_length=100)
    email = forms.EmailField()
    phone = forms.CharField(max_length=15)
    
    # Custom field-level validation
    def clean_phone(self):
        phone = self.cleaned_data['phone']
        if not phone.startswith('9'):
            raise forms.ValidationError("Phone must start with 9")
        return phone
    
    # Cross-field validation
    def clean(self):
        data = super().clean()
        if data.get('password') != data.get('confirm_password'):
            raise forms.ValidationError("Passwords don't match")
        return data
views.py — Processing the Form
def contact(request):
    if request.method == 'POST':
        form = ContactForm(request.POST)   # Bind data to form
        if form.is_valid():                 # Run all validation
            name  = form.cleaned_data['name']   # Safe, validated data
            email = form.cleaned_data['email']
            # ... save or process ...
            return redirect('success')
    else:                              # GET — show empty form
        form = ContactForm()
    return render(request, 'contact.html', {'form': form})

3.9 — Sessions & Cookies

Maintaining state across stateless HTTP

🎫 Analogy

Cookie = a paper wristband at a concert. You show it at each entry point and they know who you are. Small, visible, stored on you.

Session = a numbered token at a government office. Your number is written on a slip (cookie). The actual file with all your info (session data) is locked in their cabinet (server). You only carry the number — not your real info.

Why Do We Need Them?

⚠️ HTTP is Stateless

Every HTTP request is completely independent. The server forgets you after each request. Without cookies/sessions, you'd have to log in on every single page!

Cookies

Cookies in Django Views
# SET a cookie
def set_theme(request):
    response = HttpResponse("Theme saved!")
    response.set_cookie('theme', 'dark', max_age=86400*30)
    return response

# READ a cookie
def get_theme(request):
    theme = request.COOKIES.get('theme', 'light')  # default 'light'
    return HttpResponse(f"Your theme: {theme}")

# DELETE a cookie
def clear_theme(request):
    response = HttpResponse("Cookie deleted")
    response.delete_cookie('theme')
    return response

Sessions — Safer for Sensitive Data

Sessions in Django Views
# STORE in session
request.session['username'] = 'Sita'
request.session['cart'] = ['item1', 'item2']

# READ from session
username = request.session.get('username', 'Guest')

# DELETE specific key
del request.session['username']

# CLEAR everything (logout!)
request.session.flush()

# settings.py — configure lifetime
SESSION_COOKIE_AGE = 86400 * 30  # 30 days

3.10 — Authentication & Authorization

Who are you? What can you do?

🪪 Authentication — "Who Are You?"

  • Verify user identity
  • Check username + password
  • Login / Logout
  • First step, must happen before authorization

🛡️ Authorization — "What Can You Do?"

  • Determine permissions
  • Role-based: Admin/User/Guest
  • Resource ownership checks
  • Happens after authentication

Login Flow

Complete Login / Dashboard / Logout Views
from django.contrib.auth.hashers import check_password, make_password
from .models import Student

def login(request):
    if request.method == 'POST':
        username = request.POST.get('username')
        password = request.POST.get('password')
        try:
            student = Student.objects.get(username=username)
            if check_password(password, student.password):  # Compare with hashed PW
                request.session['student_id']   = student.id
                request.session['student_name'] = student.name
                return redirect('dashboard')
            else:
                return render(request, 'login.html', {'error': 'Wrong password'})
        except Student.DoesNotExist:
            return render(request, 'login.html', {'error': 'User not found'})
    return render(request, 'login.html')

def dashboard(request):
    if 'student_id' not in request.session:  # Protect page!
        return redirect('login')
    name = request.session.get('student_name')
    return render(request, 'dashboard.html', {'name': name})

def logout(request):
    request.session.flush()   # Clear ALL session data
    return redirect('login')

# Creating a user with HASHED password (never store plain text!)
Student.objects.create(
    username='rama',
    password=make_password('mypassword123'),  # Hashes it securely
    name='Rama Shrestha'
)
🚫 NEVER store passwords as plain text! Always use make_password() before saving, and check_password() when verifying. Plain text passwords = massive security breach.

3.12 — Middleware

Processing every request and response in a pipeline

🛂 Airport Security Analogy

Middleware is like airport security checkpoints. Every passenger (request) goes through passport control → security scan → customs before boarding (reaching the view). And on the way back (response) they go through duty-free → gate check. Each checkpoint can inspect, modify, or stop the flow.

The Middleware Pipeline

Django's Built-in Middleware

SessionMiddlewareReads session ID cookie, loads session data into request.session
CommonMiddlewareURL normalization (appends trailing slashes)
CsrfViewMiddlewareValidates CSRF token on every POST request

Writing Custom Middleware

myproject/middleware.py
import time

def request_timing_middleware(get_response):
    """Logs how long each request takes."""
    def middleware(request):
        start = time.time()
        response = get_response(request)   # Call view (and all deeper middleware)
        duration = time.time() - start
        print(f"{request.path} took {duration:.2f}s — status {response.status_code}")
        return response
    return middleware

# Register in settings.py MIDDLEWARE list:
# 'myproject.middleware.request_timing_middleware'
⚠️ Order Matters! AuthenticationMiddleware must come AFTER SessionMiddleware because Auth reads from the session. If you swap them, request.user will be empty.

3.14 — Database Types

SQL vs NoSQL — when to use what

Relational (SQL) Databases

📊 Analogy

An Excel spreadsheet — data in rows and columns, strict structure, columns predefined. Every row must follow the same format. Tables can link to each other via keys (like a "Customer ID" column in Orders table linking to Customers table).

Key Characteristics
  • Data in structured tables (rows + columns)
  • Fixed schema — columns defined upfront
  • SQL for queries
  • ACID transactions (reliable)
  • Strong relationships via foreign keys
  • Vertical scaling (bigger server)
Popular SQL Databases
  • SQLite — default in Django, file-based, good for dev
  • PostgreSQL — recommended for production, feature-rich
  • MySQL — popular in web hosting
  • Oracle — enterprise environments
  • SQL Server — Microsoft ecosystem

NoSQL Databases

📦 Analogy

A filing cabinet where each folder can contain different things — some folders have papers, some have photos, some have receipts. No strict format required. Flexible but harder to enforce consistency.

3.15 — Complete CRUD Application

All pieces together — the Notes Manager

Architecture Overview

The 4 CRUD Views

notes/views.py — All 4 operations
from django.shortcuts import render, redirect, get_object_or_404
from django.contrib import messages
from .models import Note
from .forms import NoteForm

## READ — show all notes
def index(request):
    notes = Note.objects.all().order_by('-id')
    return render(request, 'notes/index.html', {'notes': notes})

## CREATE — add new note
def add_note(request):
    if request.method == 'POST':
        form = NoteForm(request.POST)
        if form.is_valid():
            Note.objects.create(**form.cleaned_data)
            messages.success(request, 'Note added!')
            return redirect('notes:index')
    else:
        form = NoteForm()
    return render(request, 'notes/add.html', {'form': form})

## UPDATE — edit existing note
def edit_note(request, note_id):
    note = get_object_or_404(Note, id=note_id)  # 404 if not found
    if request.method == 'POST':
        form = NoteForm(request.POST)
        if form.is_valid():
            note.title = form.cleaned_data['title']
            note.description = form.cleaned_data['description']
            note.save()
            messages.success(request, 'Updated!')
            return redirect('notes:index')
    else:
        form = NoteForm(initial={'title': note.title, 'description': note.description})
    return render(request, 'notes/edit.html', {'form': form})

## DELETE — remove note
def delete_note(request, note_id):
    note = get_object_or_404(Note, id=note_id)
    note.delete()
    messages.success(request, 'Deleted!')
    return redirect('notes:index')

3.19 — Web Security Vulnerabilities

XSS, SQL Injection, CSRF — explained with examples

1. Cross-Site Scripting (XSS)

💉 Analogy

XSS is like someone slipping a poisoned note into a public bulletin board. Everyone who reads the board gets exposed. An attacker injects a <script> tag into your site's content. When other users view the page, the script runs in their browser — stealing cookies, redirecting them, etc.

❌ Vulnerable Code

<!-- |safe disables escaping! -->
<td>{{ note.description|safe }}</td>

<!-- Attacker submits: -->
<script>
alert(document.cookie);
</script>

✅ Django's Protection

<!-- Default: auto-escaping ON -->
<td>{{ note.description }}</td>

<!-- Django converts to safe text: -->
&lt;script&gt;
alert(document.cookie);
&lt;/script&gt;
<!-- User sees text, not JS! -->
🚫 Never use |safe on user-supplied content! Django's auto-escaping is your XSS shield. Don't disable it.

2. SQL Injection

💣 Analogy

Imagine a search box where you type a name to find a user. You type: '; DROP TABLE users; --. A poorly written system treats this as part of the SQL command and deletes your entire user table!

❌ Vulnerable — String Interpolation in SQL

# NEVER do this!
sql = f"INSERT INTO notes (title) VALUES ('{title}')"
# If title = "'); DELETE FROM notes; --"
# SQL becomes: INSERT INTO notes (title) VALUES (''); DELETE FROM notes; --')
# → ALL notes DELETED!

✅ Safe — Use Django ORM (always parameterized)

# Django ORM = automatically safe from SQL injection
Note.objects.create(title=title, description=description)

# Or if using raw SQL, use parameterized queries:
cursor.execute("INSERT INTO notes (title) VALUES (%s)", [title])

3. CSRF (Cross-Site Request Forgery)

🎭 Analogy

You're logged into your bank. A hacker sends you a link to a "funny cat video". That page silently submits a form to your bank: "Transfer Rs 50,000 to hacker". Your browser sends your bank cookie automatically — the bank thinks it's YOU! Django's CSRF token prevents this because the hacker's page can't know your secret token.

Hacker's page (CSRF attack)
<!-- Hidden form auto-submits to your app -->
<form id="evil" action="http://yourapp.com/notes/add/" method="POST" style="display:none">
    <input name="title" value="Hacked!">
    <input name="description" value="You've been CSRF'd">
</form>
<script>document.getElementById('evil').submit();</script>

<!-- Django blocks this because there's no csrfmiddlewaretoken!
     Returns 403 Forbidden. ✅ -->
